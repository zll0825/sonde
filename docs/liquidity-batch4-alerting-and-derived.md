# 流动性规划第四批：告警准入与派生引擎评估

> 对应 [liquidity-metrics-datasource-plan.md](./liquidity-metrics-datasource-plan.md) §5、§6、§8 第四批。
> 写于 2026-09-29，与第二、三批的接入同一分支。

## 1. 结论

- **本批不开任何告警规则。** 第二、三批新增指标全部只采集。§5 的准入门槛是按频率计的真实观测数，
  2026-09-29 用 `readiness` 查运行库：第一批指标日频只有 4 个观测日（门槛 60），周频 2～5 周（门槛 52），
  没有一条过线。门槛没到，开规则只会拿到没有分布依据的阈值。
- **通用派生引擎暂不建。** 现有派生量都能归到「插件内同源计算」或「离线脚本」两类，
  没有一条必须在线跨插件计算的派生指标。等某条离线派生量被证明有增量信息、需要实时告警时，再按 §3 的清单建。

## 2. 告警准入：`scripts/liquidity/cmd/readiness`

只读工具，按 §5 统计每个现行指标的真实观测**期数**（周频按周、月频按月去重，重复抓取不重复计数）：

```
DATABASE_URL=postgres://sonde:***@localhost:5432/sonde?sslmode=disable \
  go run ./scripts/liquidity/cmd/readiness [指标前缀 ...]
```

| 频率 | 最少期数 | 约合 |
|---|---|---|
| daily | 60 | 3 个月 |
| weekly | 52 | 1 年 |
| monthly | 36 | 3 年 |

季频、小时频不在 §5 范围内，标为 `not gated`。**过线只是必要条件**：规则上线前仍须做 §2.0 要求的离线验证
（历史回放 + 压力样本 + 与已有指标的增量信息比较），并先以 `mode: observe` 跑一段。
回填的历史算真实观测，但检测与回测只能用发布时点已可得的数据（§4）。

跨插件的派生量（后三条）目前都只需要离线计算：它们还在「是否有增量信息」的验证阶段，没有实时告警需求。

### 3.1 什么时候需要真正的派生引擎

出现下面任一情况再建，建时必须同时交付这几项，缺一项就退回离线：

1. 某条跨插件派生量通过离线验证并要上告警 → 需要**在线计算**。
2. 输入频率不同（周×日）→ 需要**对齐语义**：as-of 连接、前向填充的派生值标记为估计值，不进分位数统计（§4）。
3. 输入会被修订（H.8 基准修正、FRED vintage）→ 需要**血缘**：派生值记录每个输入的 `fetched_at`，输入改写时重算。

### 3.2 成本对比

| | 插件内计算 | 离线脚本 | 通用派生引擎 |
|---|---|---|---|
| 适用 | 同源同频 | 验证阶段的任何组合 | 已验证、需实时告警的跨源派生 |
| 代码量 | 每条几十行 | 每条几十行 | 新服务或 core 模块，含对齐、血缘、重算 |
| 运行风险 | 与源一起失败，不会错配 | 不入库，零风险 | 输入缺失、时序错配会产出错误值并触发告警 |
| 现在需要吗 | 已在用 | 已在用 | 否 |
